**증거이므로 덮어쓰지 않는다.** P2 의 모든 신규 산출물은 이 디렉터리에만 쓴다.
(2026-08-09 착수 전 4개 파일 존재 확인 완료)

## 왜 다시 재는가

포트폴리오 eco-2 가 지터 A/B 를 *"같은 머신 백투백"* 이라 서술했으나,
근거로 쓰인 두 파일이 **`stock.json` = VU 20 · `stock_fixed.json` = VU 10** 으로 **동시성이 다르다.**
즉 지터만 바뀐 비교가 아니었다. 그래서 P4 정산에서 수치를 철회했고, 여기서 **VU 를 고정해 다시 잰다.**

또 하나 — 두 파일 모두 **`confirm_conflict` 키 자체가 없다.**
k6 는 한 번도 `add()` 되지 않은 Counter 를 요약에 넣지 않으므로 **키 부재 = 0건**이다.
원인은 `PaymentApplicationService` 의 예외 재포장이었고(P2 Task 1 에서 수정),
그래서 **프리플라이트로 계측이 실제로 살아났는지부터 확인**한 뒤 본 측정에 들어간다.

## 정합성 판정

매 런 종료 직후 **`DB 최종재고 == 10000 − confirm_success`** 와 **`Redis == DB`** 를 확인한다.
이 등식이 깨지면 그 런은 성능 수치와 무관하게 **무효**다.

## ⚠️ 첫 런은 무효였다 — Hikari 풀이 10 이었다

계획서는 pool 50 을 전제했으나 `application-dev.yml` 에 **hikari 설정이 아예 없어 기본값 10** 이었다.
그 상태의 프리플라이트는 `Could not open JPA EntityManager` **403건** ·
`HikariPool.createTimeout` **207건** 이 나며 1,000회 중 **423회만 완주**했고 p99 가 **60초**(타임아웃)였다.

**커넥션 확보에서 막히면 락 경합 신호가 통째로 묻힌다.** 지터 A/B 는 재시도 분포를 보는 실험인데
모든 요청이 커넥션 대기에 갇히면 지터가 무엇을 바꾸는지 관측 자체가 불가능하다.

`SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE=50` 으로 다시 잡자 같은 1,000회가
**10분 27초 → 10.7초**, 커넥션 에러 **0건**, p95 **30.55s → 35.7ms** 가 됐다.
→ **이 디렉터리의 모든 런은 pool 50 조건이다.** (`hikaricp_connections{pool="HikariPool-1"} 50.0` 로 확인)

### 지터 A/B 결론 — **동시 개선이 아니라 교환이다**

| VU | 성공률 | 평균 지연 | p95 | 충돌 |
|---|---|---|---|---|
| 10 | 98.86% → **99.20%** (+0.34%p) | 53.1 → **66.8ms** (+25.8%) | 164.9 → 226.6ms | 114 → **80** |
| 20 | 91.44% → **94.08%** (+2.64%p) | 127.7 → **133.3ms** (+4.4%) | 381.2 → 542.6ms | 856 → **592** |

**지터는 실패를 대기로 바꾼다.** 재시도를 시간축으로 흩으니 한도(3회) 안에 성공하는 요청이 늘어
성공률과 충돌 수가 좋아지지만, **성공한 요청 각각은 더 오래 기다린다.**

**이전 판본의 "성공률과 지연을 동시에 개선(+14.7%p · −20.7%)"은 이 측정으로 재현되지 않는다.**
방향이 반대인 항목(지연)이 있으므로 그 서술은 폐기한다.

**효과는 경합이 셀수록 커진다** — VU 10 에서 +0.34%p 였던 성공률 개선이 VU 20 에서 **+2.64%p** 다.
thundering herd 는 동시에 충돌한 스레드가 많아야 생기는 현상이므로 방향이 맞다.

## 3자 전략 비교 (Task 7)

`stock.decrease-strategy` 로 교체하고 **매번 재기동**했다(`@ConditionalOnProperty` 는 기동 시 평가된다).
복원 경로는 세 전략 공통으로 낙관적 락을 유지했다 — 비교 대상은 **차감**이고, 복원까지 바꾸면 변수가 둘이 된다.
같은 머신에서 **연속 3회**, VU 20 · 10,000회 고정.

**전환이 실제로 일어났는지는 환경변수가 아니라 메트릭으로 확인했다** —
`optimistic` 에서만 `stock_optimistic_retries` 가 노출되고 나머지 둘에서는 **메트릭 자체가 사라진다.**
환경변수 오타는 조용히 기본값(optimistic)으로 떨어지므로 이 확인이 없으면 세 번 같은 것을 재게 된다.

### 결론 — **낙관적 락이 셋 중 가장 나쁘다**

성공률도 지연도 꼴찌다. 조건부 UPDATE 대비 p95 가 **3.4배**, 비관적 락 대비 **5.4배**다.

**이유는 워크로드가 낙관적 락의 전제와 반대이기 때문이다.** 낙관적 락은 *"충돌이 드물다"* 를 전제로
락 비용을 아끼는 기법인데, 이 측정은 **단일 상품 행에 VU 20 이 전량 몰리는 조건**이라 충돌이 상시다.
그러면 재시도가 곧 낭비가 되고, 한도(3회)를 넘긴 5.44% 는 아예 실패로 끝난다.

**나머지 둘이 100% 인 이유는 충돌 개념 자체가 없기 때문이다** —
조건부 UPDATE 는 `stock >= :qty` 를 UPDATE 에 실어 DB 가 원자적으로 판정하고,
비관적 락은 행을 잠가 직렬화한다. **재시도할 일이 생기지 않으므로 재시도 메트릭도 0 이다.**

**비관적 락이 가장 빠른 것은 이 조건 한정이다.** 임계 구역이 짧고(재고 한 줄) 경합이 극단적이라
직렬화 비용보다 재시도 낭비가 컸다. 임계 구역이 길거나 경합이 드문 워크로드에서는 뒤집힐 수 있다.

### `maxAttempts` 판정

계획서 기준은 *"`_max` < 3 이고 `confirm_conflict` 가 1% 미만이면 3 유지"* 였다.
실측은 **`_max` = 3(한도 도달) · 충돌 5.44%(VU 20)** 로 **두 조건 모두 불충족**이다.

그러나 **한도를 올리는 것은 답이 아니다.** 한도를 키우면 실패가 지연으로 바뀔 뿐이고,
같은 조건에서 **전략을 바꾸면 실패와 지연이 동시에 사라진다.**
→ 결론은 *"`maxAttempts` 를 몇으로 할까"* 가 아니라 **"이 워크로드에 낙관적 락이 맞지 않는다"** 다.
